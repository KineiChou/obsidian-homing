# 目录分类：混合深度候选与统一决选

状态：混合深度分类、结构摘录和可选元数据画像已实现并有合成测试。固定示例 API 冒烟不代表真实知识库分类质量；组大小、提名数和预算不是效果承诺。官方能力核查于 2026-09-22。

## 决策

将每个允许直接存放笔记的目录视为一个目标，完整路径提供层级上下文。候选在数量和上下文预算内时，一次比较全部目标；超出单题限制时，各组提名多个目标，再统一决选。目录树不作为单路径的硬过滤器。

这里的“提名 → 决选”是模型判断的两个阶段，不是从最深目录向父目录回溯。允许直接归档的父目录和子目录可以在同一阶段参加，最终结果仍是具体存放位置，不提升成一个更粗的父分类。

首版不建设嵌入索引，不扫描全库正文，不根据顶层目录先淘汰子树。更大规模且具有明确语义层级的目录树，再评估保留多个分支的搜索。

## 为什么逐层判断可能失败

例如以下目录都可能涉及语音识别：

```text
Projects/
  语音识别实验/
Resources/
  AI/
    语音识别/
```

笔记写着“语音识别实验本周验收记录”，顶层只看到 `Projects` 和 `Resources` 时，需要先猜用途，再进入子目录。一旦选错顶层，具体项目名再吻合也无法挽回。完整路径与明确的“项目交付记录／通用技术资料”说明让相关证据在首次比较时可见。

如果笔记只有“语音识别原理”，而用户没有表达是通用资料还是项目素材，完整目录树也无法补足这个意图。此时应允许用户改选或保留待整理。不要默认所有用户都采用 PARA 的规则。

顶层可能表达状态、时间、责任范围或使用场景，下一层才表达主题，文件系统层级不保证是逐级细化的主题分类。给父节点补充子树摘要能缓解信息不足，但单路径搜索依然会过早排除其他分支。TypeSafe 的官方示例也明确区分贪心搜索的不可恢复误判与保留多路径的搜索。[官方分层分类](https://docs.typesafe.ai/cookbooks/hierarchical_classification)

## 方案比较

| 方案 | 实际做法 | 优点 | 主要代价与风险 | 采用范围 |
| --- | --- | --- | --- | --- |
| 单路径逐层 | 每层只选一个子目录，继续向内 | 每题短；目录语义明确时容易理解 | 早期错误不可恢复；深度增加串行轮次；宽节点仍可能超限 | 不作为默认 |
| 多分支逐层 | 每层保留若干可能路径，继续展开 | 有机会利用深层证据纠正早期歧义 | 仍会剪枝；需要分支说明、停止条件与路径排序；有多轮依赖 | 大规模且层级语义明确时评估 |
| 全量混合深度 | 所有实际目标在同一题比较 | 无提名阶段的召回损失；浅层与深层直接比较 | 受单题选项与上下文限制；相似目录仍需清晰说明 | 预算允许时默认 |
| 分组混合深度 | 全部目标分组，各组提名多个，再统一决选 | 每个目标先被评估；避免顶层名称决定去向 | 提名仍会遗漏；通常至少两轮，输入成本高于只走一条分支 | 超出单题限制时默认 |

“分组”不是先选一个组再进入它，而是所有组都参与提名。它把裁剪移到已经看到实际目标用途之后，但不能消除裁剪风险。

## 目标目录如何描述

基础目录项来自目录树与用户设置：

| 字段 | 含义 |
| --- | --- |
| `id` | 当前目录快照内的本地标识，用于校验模型选项 |
| `path` | 知识库内完整路径，保留同名目录的上下文 |
| `acceptsNotes` | 是否允许笔记直接放入此目录；关闭不代表排除它的子目录 |
| `directPurpose` | 可选：什么笔记应直接放在这里 |
| `subtreeRules` | 可选：用户明确指定对子树生效的约束；与祖先同类规则一起提供 |

普通目录默认可以直接归档，用户可将它标为仅组织子目录的容器。不得根据“目前没有 Markdown 文件”把空目录排除，也不得强制只归到叶子目录。排除整棵子树是独立设置。

例如 `Resources/AI` 的分支范围可以是“AI 相关资料”，但其直接存放用途应更具体，例如“AI 总览及横跨多个子主题的资料”；`Resources/AI/机器学习` 则承接机器学习专项资料。直接用途不自动继承为子目录用途，明确的子树规则才向下传递。

候选描述包含完整路径、自身直接用途、祖先与自身的显式子树规则。缺失说明就保留为空，不从其他笔记推断规则。模型先遵循用途约束，再判断主题是否匹配；当具体目录有充分证据支持时选它，不能仅按深度偏爱子目录，也不能因父目录描述宽泛就把全部笔记吸走。

## 单题与上下文限制

当前官方 Choice 上限为 **255 个选项**。每题预留 `unassigned` 后可放 254 个真实目标；知识库总目录数可以更多。[Choice](https://docs.typesafe.ai/primitives/choice)

当前模型还有两项独立预算：整个请求的 `state` 加所有问题最多 64k tokens；`state` 加最长单题最多 32k tokens。即使少于 254 个目标，也可能因说明太长需要分组。多个独立问题可共享一次请求的笔记状态，但决选依赖第一阶段答案，必须后发。[Models](https://docs.typesafe.ai/models)

实际插件采用代码中的保守字节预算：状态加最大问题 30,000 UTF-8 字节、整包 60,000 字节，记录服务返回用量；不是精确 tokenizer。`prepareNote(note, longNoteStrategy)` 默认将超过 12,000 UTF-8 字节的正文整理为标题大纲、开头和章节开头组成的结构摘录，并返回原文／发送字符数。全文策略不摘录，超限报错；任何策略都不静默裁剪目录用途规则，源 SHA-256 始终基于完整原文。

批量确认前用目录元数据大小和文件大小模拟常规分组打包，生成请求范围及推荐篇数；不读取所有正文，不包含重试，也不是费用保证。真实发送仍经过共享额度预留。

### 可选目录画像

`folderProfilesEnabled` 默认关闭。启用时，`MemoryFolderProfiles` 从已有元数据维护最多 20,000 篇标题和标签，每个目录最多采样 8 个标题、16 个不同标签，允许这些有限元数据随目录描述发送，不读取候选正文。画像不替代人工用途和子树规则。

候选超过 254 时可以用笔记标题、标签、有限正文与目录路径／用途／画像的词项重合做本地预筛：只有足够明确且不过于分散的信号才限制到 64 个候选，保留有人工说明的目标；弱信号或保护目标过多时回退完整分组。该启发式有召回风险，尚无真实语料质量结论。

## 算法与初始参数

### 1. 固定输入快照

从 Obsidian 的目录对象与插件设置构建目标集合，排除 inbox、排除子树和仅作容器的目录。保存目录快照版本、规则版本、模型和提示版本，与当前笔记内容指纹绑定。多批次使用同一个已验证的具体模型版本，避免模型别名在任务中途切换。空候选直接显示人工处理入口，不调用 Jev。

若全部目标不超过 254 且一题可容纳，直接执行最终 Choice，包括 `unassigned`，随后进入确认。无需额外提名。

### 2. 构造分组

超出单题范围时，按完整路径的稳定散列排序后依序装组；默认每组最多 64 个真实目标，并根据单题 UTF-8 字节预算提前封组。一个组可以混合任意深度和不同顶层的目录，各目录的完整路径和用途仍然可见。

稳定散列用于分散物理目录邻接关系，不参与相关性评分。它只是一种简单、可复现的装组方式，不保证最优。目录快照变化后重新构造分组；本地标识与真实路径映射始终重新校验。

初始提名数 `k = 3`。组数最多 64，提名集合最多 192 个真实目标，再加一个 `unassigned`；最终问题也必须满足单题上下文预算。所有这些限制都由本地代码检查。超过预算提示缩小允许范围或人工归档，不任意减少某组的名额，也不自动再套多轮淘汰。

### 3. 每组都执行提名

每组一个 Choice，问“这些实际目录中，哪个最适合直接存放当前笔记”，选项带上述目录描述和 `unassigned`。所有问题使用同一笔记快照。按请求预算将独立组问题打包，多个 HTTP 请求仍受公共队列的并发与费用限制。

收到组内完整概率分布后，取最多前三个真实目录，过滤 `unassigned`，同时保留该组的放弃信号。即使 `unassigned` 排第一，也不据此提前丢弃整组，由最终题统一判断。若真实目录在提名边界同分，记录歧义；为确保有界执行，使用稳定路径顺序打破并列，明确这部分可能产生召回损失，不把它当作模型已作出可靠区分。

组内的 0.8 与另一组的 0.6 不能直接比较：它们面对不同的竞争集合。提名只使用各组内部次序，不跨组用阈值过滤，不按最高概率只保留少数组。

任何组失败、超时或未处理，整个分类任务都尚未完成。允许在相同快照下有界重试失败组；不能把失败当作无匹配后继续产出完整推荐。

### 4. 统一决选

把所有提名目标放入同一个最终 Choice，仍使用原笔记快照、完整路径和用途规则，并提供 `unassigned`。不附带组内概率、排名或组名，避免把不可比较的分数当作先验。

最终题的业务规则与全量单题相同：符合笔记用途，在有证据时选择更具体的位置；用途不明或无合适目标时放弃。日常界面只展示一个推荐位置并要求确认；用户主动更改位置时才展开完整目录选择。原始模型评分不转换成正确率，交互细节见 [低打扰交互](interaction-design.md)。

这里的统一决选覆盖的是“本轮提名集合”，不能称作对所有目录的无损排序。最终放弃也不证明整个知识库不存在可用位置。人工目录选择器始终包含当前允许范围内的全部目标。

### 5. 防止失效结果

分析期间源内容、目录快照或分类语义配置变化使该任务失效，停止后续批次并丢弃旧响应。已完成建议在无关目录变化后允许保留选中目标并映射目录版本；目标失效或无目标建议需要重新判断时，可按自动设置稳定等待后重排。历史 waiting 库存不会因目录事件自动上传。新建目录且目录清单因此多出可选目标时（含改选时新建），自动归档开启下，已保留的建议在稳定等待后于后台重新判断一次：判断期间仍显示原建议，得到新结果才替换，失败（含额度用尽）保留原建议；新目录在判断完成前被重命名时，后台判断重新排队。收件箱内或被排除的目录不触发。确认计划仍严格校验内容、目标、相关版本和冲突。最小建议持久化与 schema 2 恢复规则见 [开发契约](development.md)。

## 一次 600 个目录的例子

设有 600 个实际目标，各描述较短：

1. 组成 10 组：9 组各 64 个，最后一组 24 个；每个目标都在其中一题出现。
2. 每组提名 3 个，形成最多 30 个目标。
3. 使用一个含 30 个目标与 `unassigned` 的 Choice 决选。
4. 展示建议，等待用户确认。

这共涉及 11 个 Choice 问题，而不必发 11 次 HTTP 请求。如果提名的 10 题可装入一次请求，则共两次请求；否则是若干提名批次加一次决选。不得把第一阶段与依赖它的决选一起发送。

令笔记状态大小为 `S`，提名批次数为 `B`，全部提名问题大小为 `P`，决选问题为 `Q`，输入预算近似为 `(B + 1) × S + P + Q`，还需预留结构开销。每个跨请求批次都会重新发送状态。因此这比只选一个分支消耗更多输入，优势是每个具体目标都先有参与机会。

## 与轻量运行的关系

- 初始化只从 Obsidian 已维护的目录树获取路径，目录创建、移动、改名、删除及配置修改时增量更新缓存；不轮询磁盘，不读取每个目录下的笔记来生成摘要。
- 用途来自可选的用户设置。目录描述与分组方案在快照不变时复用；针对不同笔记的模型分数不能复用。
- 自动归档在 inbox 笔记稳定后触发，一份内容版本只有一个自动任务；不跟随每次按键运行这套分类。编辑时链接建议继续使用独立的局部查询机制。
- 分类获取当前笔记的一份稳定内容，提名与决选共用它。只有当前待分类笔记的读取、队列记录及后续确认操作有各自必要的 I/O；目录候选比较不引入全库正文读取。
- 请求预算与编辑辅助共享，批次之间允许编辑任务优先，失效或暂停后不继续发送后续批次。

## 何时值得用多分支逐层

当实际目标远超上述预算，并且目录确实构成明确分类体系时，可评估束搜索：例如每层保留三条路径，节点描述包含分支用途与有区分力的后代信息；允许停在可直接存放的父目录，也允许继续下降或放弃。

只保留三条路径仍可能剪掉正确分支，不能宣称完全纠错。官方示例用路径边概率的几何平均作排名；这只是路径搜索启发式，不能解释为笔记归档正确率。若采用此方案，应将保留的真实落点再放进同一题比较，不能直接用不同深度的路径概率决定最终位置。[官方示例](https://docs.typesafe.ai/cookbooks/hierarchical_classification)

另一种待评估提名方法是用统一问题对每个目录独立判断是否合适，再取候选进行 Choice 决选。它可以避免组内竞争改变归一化分数，但每个目录都需一个问题，输入开销与分数校准仍需验证。只有分组召回确实成为主要误差来源时，再比较此方法，首版不同时实现多个调度体系。

## 最小评估

使用用户允许发送且预先标注的中文及中英混合样本；可接受目标允许多个，也允许“意图不足”。先比较单路径逐层、多分支逐层、全量混合深度与分组混合深度。在目标数不超过 254 的子集上也强制分组，可直接观察分组带来的损失。

分别记录：

- 提名召回率：人工认可的至少一个目标是否进入最终集合。这是决选能够成功的前提。
- 最终首选与前三命中率：在全部样本与提名成功样本上分别报告，分清遗漏与判断错误。
- 无合适位置／意图不足的识别，以及高模型评分仍然选错的案例。
- 改变组大小、每组保留数量和分组顺序时的结果稳定性。
- 实际请求数、输入 tokens、总延迟、用户改选与确认时间；不把问题并行等同于成本免费。

关键样本包括无语义的顶层名称、同名子目录、浅层父目录可存放、空目录、用途相似但项目不同、同主题跨多个顶层，以及真正无匹配的笔记。对照“路径”与“路径加用途说明”，先验证说明是否解决歧义，再决定增加搜索算法的复杂度。
