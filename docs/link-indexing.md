# 双链候选的轻量索引与匹配算法

状态：压缩前缀树、宿主接入和编辑推荐已在 0.1.0 开发预览实现；另三种方案作为比较与后续候选。**当前的词条、匹配、打分、分层与模型调用规则以 [双链匹配设计](link-matching.md) 为准**，本文保留为索引结构与方案比较的背景。本文细化 [双链补齐设计](link-suggestions.md) 中的文字识别与目标召回。

## 1. 资源边界

自动推荐中的本地匹配与候选查询只访问内存：编辑器中的局部文本、插件的紧凑元数据索引和已缓存的目标描述。默认不读其他笔记正文，不执行 grep，不按输入次数扫描文件列表，也不持久化每次本地查询结果。真正发送 Jev 请求时另行更新少量本机额度记录，不把整条联网流程宣称为零存储操作。

grep 主要带来读取、遍历与重复匹配；操作系统缓存可能减少物理读盘，但不能消除全库扫描的 CPU 和内存带宽成本。本文的“零文件读写”只指插件一次自动候选查询主动发起的文件操作，不包括 Obsidian 自身的打开文件、保存和元数据索引。

索引的基础数据来自 `vault.getMarkdownFiles()` 和 `metadataCache.getFileCache(file)`；后者可能返回空，需等待元数据就绪事件，不以读取正文作为补偿。[Obsidian 公开 API](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)

## 2. 四种方案比较

记号：N 为笔记数，S 为标题／别名总字符数，P 为本次处理文本长度，L 为自动匹配允许的最长词条，Z 为匹配输出数，R 为本次遍历的倒排条目数。复杂度包含输出；大量重叠命中不能视为免费。

| 方案 | 如何找到文字位置 | 如何得到目标 | 查询成本与磁盘 | 能力边界与代价 |
| --- | --- | --- | --- | --- |
| A. 压缩前缀树 Radix Trie | 从局部文本的合法起点沿压缩词条前缀匹配，命中时直接得到原文起止位置 | 终点关联 termId，再查 termId → docId 列表 | 约 O(P×L＋Z)，默认零文件操作；内存 O(S＋词条与目标关联数) | 支持标题／别名明确提及；不能识别任意同义改写；单条增删方便 |
| B. Aho–Corasick 自动机 | 将所有标题／别名编译成多模式匹配器，一次扫描局部文本 | 命中词条直接取得其 docId 列表 | 常数时间转移假设下 O(P＋Z)，零文件操作 | 识别能力与 A 相同；增加失配／输出链接，词典变化需批量重建或复杂的增量结构 |
| C. 元数据倒排索引 | 用户选中的文字，或本地分词后枚举的有限连续短语 | 标题、别名、标签及自填描述的 token／字词片段 → docId，再排序 | 约 O(R＋候选排序成本)，零文件操作；常见词的 R 可能很大 | 支持部分词重合、近似标题；不能保证语义同义；需要控制短语枚举和高频倒排列表 |
| D. 向量检索 | 段落向量本身不提供位置；还需选中文字或枚举短语 | 近邻索引召回语义相近笔记，再让 Jev 判断 | 每次需向量编码与检索；已驻留索引时可零文件操作，建库及更新更重 | 改写召回潜力更大；需另一个 embedding 模型，增加模型、向量、索引与持久化成本 |

**建议选择 A 作为默认自动路径，C 作为后续按需搜索增强。** B 只在真实长文本匹配数据证明 A 不足时替换；D 暂不进入轻量首版。三种非向量方案都可以避免查询时读盘，差别主要在匹配能力、内存及更新复杂度。

### A. 压缩前缀树：默认方案

普通 Trie 为每个字符设置节点；压缩前缀树把连续的单分支字符合成一条边。例如 `Transformer` 可保存在一条边上，插入 `Transfer` 时才分裂共同前缀 `Transf`。节点只保存必要分叉与词条终点，避免每个字符都对应一个 JS Map。

匹配时沿边比较当前文本，不创建全部子串，也不遍历所有标题。`Transformer` 和“机器学习”命中后，原文范围与词条 ID 同时得到；词条终点已经关联候选笔记，不需要再执行一次全库搜索。

最坏情况仍可能在许多起点反复比较长前缀，因此要约束 P、L、输出数与每次处理时间，不能仅依赖平均耗时。

### B. Aho–Corasick：适合稳定词典与较长输入

该方案给 Trie 增加失配链接，失败后复用已匹配的后缀，避免从每个位置重新开始。常量转移查找条件下，扫描成本随输入与输出增长；若使用排序数组和二分查找存储转移，还应计入查找成本。

新增词条可能改变已有状态的失配关系，不能简单挂一条树枝就认为更新完成。朴素实现应合并事件后重建，在新索引可用时替换旧索引；构建期间仍查询旧版，旧推荐通过索引版本校验失效。后台重建会短暂同时保留两个索引，内存峰值必须计算。

“静态自动机＋增量 Trie＋删除标记”可以减少重建，但引入双索引查询与版本合并。当前输入被限制在约千字的局部文本，先不增加这套机制。

### C. 只索引元数据的倒排检索

每篇笔记只索引名称、别名、标签和可选的自填描述；不构建正文全文索引。拉丁文本按词切分，中文可使用相邻双字片段。例如“注意力机制”产生“注意、意力、力机、机制”。

构建 `token → docId 列表`，同一篇笔记的重复 token 只记一次，并记录字段来源。查询时优先取低文档频率的 token，遍历对应列表，将命中的候选累加评分。可使用字段加权重合或 BM25；缺少实测收益时，先用简单重合排序。

自动识别位置时，可用运行环境的 `Intl.Segmenter` 获取局部分词边界，枚举最多 24 个连续短语，每个最多 6 个词，保存原文范围；原文不能被词袋重组。每段总倒排访问上限建议 2,000 项，超过则停止自动扩展，提供手动搜索。共同出现的零散词不能被包装成一个不存在的短语。

这类枚举可能漏掉中文专业词。因此 C 更适合首先用于“选中文字 → 搜索链接”，也可给 A 已定位的词提供更多候选；没有明确原文锚点时只展示相关笔记。元数据里完全没有共享词语的同义表达仍可能漏掉。

### D. 向量召回：保留为可选能力

将每篇笔记的指定内容编码成向量，查询时为当前文字编码，用近邻搜索返回少量候选。Jev 继续做最后选择。Jev 的 Choice 接口不能直接替代 embedding 服务；这里需要另一个模型。

仅以 20,000 篇笔记、384 维 float32 计算，原始向量占 `20,000 × 384 × 4 = 30,720,000` 字节，约 **29.3 MiB**；100,000 篇约 146.5 MiB。还未包含向量索引、模型权重和推理工作区；正文切块会进一步增加向量数量。量化可以减小向量存储，但改变精度和实现复杂度。

HNSW 等近邻索引可减少检索工作，但返回的是近似候选，性能还取决于维度、数据分布和查询参数，不能承诺固定 O(log N) 或固定准确率。[HNSW 原始论文](https://arxiv.org/abs/1603.09320)

## 3. 默认方案的数据结构

```text
documents[docId]
  file: TFile 引用
  metadataRevision
  contentRevision
  termIds: 该文件贡献的词条 ID
  tags / 可选 description: 有长度上限的元数据

phraseTree
  压缩边: label + child
  终点: termId

targets[termId]
  docId 列表 + membershipRevision

decisionCache
  有容量上限的内存 LRU
```

完整路径从当前 TFile 取得，用于展示与解析；docId 是会话内的文件身份，不把路径字符串复制进每个词条。两个目录中的同名笔记拥有不同 docId，同一个词条指向多个 docId。

首版自动词条来源限定为文件名去掉 `.md` 后的名称和 `aliases`，暂未索引 frontmatter title 属性。其他标题、标签和目录名称仅用于候选描述或消歧，不都变成主动补链的词条。

同一文件的规范化名称／别名先去重，再计算新旧 termId 集合的差异，避免删除一个别名时误删同文件的同名标题关联。字段处理也要有上限：例如最多 32 个自动别名、8 个参与消歧的标签、自填描述最多 160 个 UTF-16 单元。当前截断字段，覆盖受限的专用提示尚未实现；不在一次事件中展开无界字段或对整份属性对象计算哈希。

首版只折叠 ASCII 大小写，保持其他字符原样，不去除标点、不合并空格、不移除重音。这样不会因字符长度改变造成写入错位。Unicode 规范化、繁简转换及跨语言改写可通过显式 aliases 支持，后续若加入自动归一化，必须保存规范化位置到原文位置的映射。

自动词条建议限制为 2–64 个 UTF-16 单元，另校验起止点不切开代理对或组合字符。当前没有单字开关或全库手动搜索入口；较短 aliases 可让超长名称进入自动匹配。

## 4. 索引生命周期：更新元数据，不扫描正文

### 冷启动

1. workspace 就绪后订阅元数据与文件事件，避免初始遍历期间漏掉更新。
2. 获取一次 Markdown 文件列表，分批读取已有元数据缓存。建议每批最多 250 篇且主线程工作不超过约 4 ms，然后让出执行权。
3. 名称可以立即索引；aliases 缓存未就绪时等待 `metadataCache.changed` 补齐，不调用 `vault.read`。
4. 每批使用当前文件及最新描述，删除事件和新版本优先，防止把已删除文件或旧别名写回索引。
5. 初始索引尚未完整时显示准备状态，不将“未命中”解释为不存在。索引只初始化一次，编辑器窗口共享一份。

基础索引直接来自 Obsidian 已维护的元数据，默认不另存一份磁盘索引。重启时重建这份小索引，换取较少的同步、缓存版本迁移和磁盘写入逻辑；若冷启动实测过慢，再单独评估持久化。

### 增量更新

| 事件 | 处理 |
| --- | --- |
| 只有正文改变 | 不重建词典；增加文件内容版本，令涉及该目标的旧请求失效 |
| aliases／title 改变 | 对比新旧有限字段，移除该 docId 的旧关联，插入新增词条 |
| 标签／自填描述改变 | 更新目标描述与版本，不改文字匹配树 |
| 文件改名／移动 | 更新文件身份映射、必要的名称词条及展示路径 |
| 文件删除 | 用 documents[docId].termIds 删除关联，空词条从树中移除并压缩路径 |
| 目录整体改名 | 更新受影响子树，不假定每篇子文件都收到单独的改名事件 |
| 大批量同步 | 当前按宿主事件增量处理；专门的同步风暴合并队列尚未实现 |

处理 `metadataCache.changed(file, data, cache)` 时只读取需要的 cache 字段，不复制、保存或计算整份 `data` 的哈希。元数据事件不会覆盖文件改名，因此另监听 vault 的 rename/delete。[官方事件定义](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)

## 5. 每次编辑的完整算法

### 记录变化

用 Obsidian 注册的 CodeMirror 6 扩展观察 `docChanged` 和变化范围。补链按键回调更新文档版本、合并有限脏区间、映射未受影响建议并重置计时器，不执行检索、网络或 `editor.getValue()` 全文复制；若该笔记同时有归档建议／分析任务，宿主另行使归档待办失效并保存少量状态。CodeMirror 提供变化集合与位置映射，可用于跟踪区间。[ViewUpdate 源码](https://github.com/codemirror/view/blob/main/src/extension.ts)、[ChangeSet 源码](https://github.com/codemirror/state/blob/main/src/change.ts)

停止输入约 1 秒且输入法 composition 结束后，读取变化所在的局部普通文本块。使用编辑器已有语法树排除链接、代码、属性和公式；语法树尚未解析到所需区域时跳过或稍后检查，不在按键回调里强制解析整篇。

`snapshot()` 是无副作用读取：返回当前文字、版本和可选 dirtyRanges，不清除待分析范围。只有同一快照分析成功或确认没有候选时，协调器才调用 `acknowledgeAnalysis(snapshot)`；该方法校验会话与文档版本，仅移除已分析窗口内的脏区间。失败、超时、取消和过期结果不消费任务；确认预览及多个消费者读取快照也不会抢先清空自动分析范围。

局部窗口预算 P≤1,200 UTF-16 单元；frontmatter 笔记另读开头最多 1,200 单元作保护，未找到闭合则整篇跳过补链。扫描范围围绕变化区向两侧补最多 L−1 个单元，以发现横跨插入点的词条，补边也计入预算。若完整段落超限，使用当前句子或有明确原文边界的窗口，并说明该次只分析局部；不能向 Jev 宣称它看过整段。

多处编辑最多保留 8 个脏区间；大批粘贴不自动排队分析整篇，优先当前编辑区域，其他内容由手动命令触发。开闭代码围栏等结构修改可能影响远处语法，应使相关旧建议失效，而不是只按字符距离推断安全区域。

### 匹配与目标获取

伪代码表达查询职责，省略预算与语法校验的具体 API：

```text
for start in eligibleTextStarts(window):
    node = phraseTree.root
    at = start
    while edge = node.childStartingWith(window[at]):
        if window does not match edge.label at at: break
        at += edge.label.length
        node = edge.child
        if node has termId and boundariesAreValid(start, at):
            emit { from: start, to: at, termId: node.termId }

for mention in resolveOverlaps(matches):
    candidateIds = targets[mention.termId]
    filter sourceNote, excludedTargets, existingLinks, deletedFiles
    rank the remaining IDs using bounded in-memory metadata
    return { exactOriginalRange, originalText, candidateIds }
```

匹配边界：拉丁单词不嵌在更长标识符中；中文使用完整词条匹配。重叠结果默认选择同起点的最长词条，再选择不重叠区间。原始命中预算建议 128 个，达到上限就标记本次结果不完整，避免常见短词产生大量输出。

目标列表通常很短，不需要倒排检索。若同一词条关联超过 128 篇笔记，默认停止该词的自动推荐；当前可借助原生链接搜索；不能扫描任意长列表，也不能按路径顺序取前几篇后宣称目标明确。

候选少量消歧时，从当前上下文生成有限 token，去掉锚点自身的共同 token，再比较各目标的标签、其他名称和路径词的重合。首版可按“标签命中数、其他名称命中数、路径命中数”依次排序；这是召回启发式，不是正确率。默认保留 8 篇，上限 20；若截断处仍并列则跳过该处，不让路径排序替代语义判断；尚未展示单独的覆盖受限提示。

自动检测复用已解析目标集合，当前窗口检查语法。用户确认时才额外扫描当前编辑器全文，检查尚未保存的重复链接；按键和自动候选查询不复制全文。

### Jev 与结果缓存

本地没有命中时不调用 Jev；有候选时，每处文字一个 Choice，附 `none`。标题、路径、aliases、标签和用户自填的短描述已经能组成请求，默认不加载候选正文。

建议每次最多 3 处提及，候选默认 8 篇；设置全局一个在途请求，自动请求启动间隔至少 5 秒，限制待发送队列只保留当前最新任务。网络请求已发送后丢弃旧响应，并不代表费用被取消；传输层不能真正取消时也不能不断释放并发名额再发新请求。

内存 LRU 键包含规范化提及、局部上下文、源路径、完整候选元数据、相关设置／提示／模型版本；不包含文档 revision 或绝对锚点偏移。缓存命中后使用新的输入锚点生成建议，确认计划继续检查原文与编辑版本。缓存最多 256 条且总载荷不超过 2 MiB。相同输入直接复用，包括 `none` 结果；仅更换候选描述也需要失效。

用户的“本次不再提示”和主动撤销插入使用独立的有界会话抑制记录，不与上述结果缓存混用。该记录随编辑会话释放，按源身份、映射后的锚点及目标身份匹配；别处编辑、正文保存或候选版本变化不解除抑制。锚点被改成其他内容或用户明确重新查找该区域时再解除。结果缓存失效不能被解释为用户已允许再次提示。

词典成员发生变化时更新 catalogueEpoch，使“先前无候选”的缓存失效；正文自动保存且名称未变时不提升词典 epoch，不把每次输入变成全索引失效。补链结果缓存只在内存，本地检索不调用 saveData；归档建议失效和实际网络请求的本机额度持久化独立处理。自动补链请求及其重试受每日总额度 30%（向下取整）的子额度限制；额度用尽不全局暂停归档或手动补链。

## 6. 后续可选：按需读取正文

当前没有实现候选正文读取。若后续增加“补充内容再判断”，应满足以下边界：

- 每次最多读取 3 个候选，事先用已有文件大小信息跳过超过 128 KiB 的文件；`cachedRead` 也可能需要实际读盘，不能假定免费。
- 从已读取内容选取与上下文有关的短段，单篇最多发送约 800 字符。立即释放整份正文，只把短摘录放入有容量限制的内存缓存。
- 摘录缓存以 docId＋内容版本为键，移动、删除、修改后失效；建议最大 2 MiB，不写入插件日志或持久化索引。
- 界面说明新增的数据发送范围，并计数本次主动读取文件数。

未来此入口应与自动匹配路径分开，因此“实时自动推荐不读取候选正文”仍成立。未来若引入正文索引或 embedding，应明确增加首次构建和后续更新成本。

## 7. 性能目标与小型对照

以下是目标预算，不能整体当作已达成的插件指标；生产实现测量见本节后续链接：

| 项目 | 初始目标 |
| --- | --- |
| 每次自动候选查询 | 插件主动文件读写 0 次 |
| 每次输入事件回调 | 不做检索／网络／全文复制，目标 p95＜1 ms |
| 本地匹配＋候选过滤 | 规定文本预算下 p95＜5 ms，不含等待时间及网络 |
| 索引初始化与增量批次 | 主线程每批约 4 ms 后让出，不阻塞启动 |
| 自动提及／候选 | 每次最多 3 处；每处默认 8 篇、最多 20 篇 |
| 索引内存 | 20,000 篇、约 40,000 个受限词条下，额外常驻堆先以 32 MiB 为目标，需包括词条与元数据实测 |
| 请求／摘录缓存 | 各自最多 2 MiB；首版索引无持久化写入 |

不能把估算的字符字节数当成真实 JS 堆大小。当前索引随知识库规模增长，没有按实际 JS 堆自动限流的机制；需在真实大库测量峰值，再决定是否新增带明确提示的范围限制。当前固定上限约束查询工作量和候选字段，不是全索引内存的硬上限。

### 已完成的合成实验

脚本：[link-matching.mjs](../benchmarks/link-matching.mjs)。原始结果：[link-matching-results.json](../benchmarks/link-matching-results.json)。运行：`node benchmarks/link-matching.mjs`。不需要依赖包，不访问知识库或网络。

环境：macOS arm64、Node 22.21.1；每种方法在独立子进程运行。语料为固定种子生成的中英文名称，共享部分主题前缀，每篇约两个词条。每组 160 个约 950–1,010 UTF-16 单元的查询，含有命中与无命中场景；先预热，再计时。

20,000 篇、40,003 个词条的单次运行：

| 方法 | 建索引耗时 | 匹配 p95 | 额外索引堆 |
| --- | ---: | ---: | ---: |
| 内存逐词 indexOf 基线 | 0.02 ms | 4.93 ms | 接近 0 MiB |
| 压缩前缀树 | 21.64 ms | 0.008 ms | 13.66 MiB |
| Aho–Corasick，Map 转移 | 26.36 ms | 0.009 ms | 18.29 MiB |

这些数字只用于比较本次实现的匹配结构：堆差额排除了共有输入词条、目标元数据、postings、构建峰值和编辑器；耗时排除了语法解析、Unicode 归一化、边界过滤、索引更新和 Jev。数字不能当作完整插件内存或响应时间，微秒级差异也不足以判断两个快算法的普遍胜负。

实验结果支持暂不为短窗口引入自动机复杂度；不证明所有词典上 Radix 都更快或更省内存。需要在真实标签分布、极长共同前缀、密集重叠短词、同名目标很多、首次启动和批量同步中验证预算。C 与 D 本轮未实现，不能将它们的效果或耗时当成已测数据。

### 需要保留的验证

- 三个词条匹配器与 indexOf 基线核对原始范围和词条 ID；现有脚本覆盖合成样本、前后缀重叠和部分 Unicode 情形。
- 接入后分别检查索引增删、改名、目录整体移动、缓存空值、构建期间更新与重启，不只比较静态查询。
- 用真实标注衡量位置覆盖、Recall@8／20、Jev 条件选择准确率与最终推荐精确率。
- 使用插件文件访问计数器验证自动路径确实为零；DevTools 观察长任务、常驻堆、GC 与初始化峰值。
- C 的增量收益明显时再增加倒排索引；D 需要同时证明召回收益与资源预算可以接受。
